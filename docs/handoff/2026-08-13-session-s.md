## 1. What shipped

- **Schema (additive):** Lottie `phases.source` grows `'composition'`; video phases gain an
  optional `source` (absent ⇒ manual-equivalent — pinned by a no-injection test) and both kinds
  gain optional `holdAt` (clip-native units). Stored `introEnd`/`outroStart` are IGNORED under
  follow but stay present — the Detach landing.
- **ONE derivation:** `followWindowMs` (`@cg/shared-schema/follow-window.ts`, ms — video's native
  unit, consumed directly) + `lottieFollowWindow` (`@cg/lottie-bridge/timing.ts`, the frames↔ms
  adapter). `followsComposition()` is the one spelling of "is this a follower". The model is the
  continuous window anchored at the HOLD time `H` — the owner's 5 s/3 s/2 s case is tested
  verbatim in ms, in animation frames, and through `createRuntime` + `tick(frame)`.
- **Driver capability:** `introStart`/`outroEnd` (Lottie) and `introStartMs`/`outroEndMs` (video)
  window bounds, honoured inside the ONE mapping per kind (`clipPositionAt` / `expectedClipMs`
  and its inverse); defaults are the clip's own bounds, so every existing construction is
  untouched (asserted).
- **Runtime resolution:** the settle aggregation is now a PRE-PASS so the effective content start
  exists at driver construction; a follower is fed the marker-less shape (`settleOffset: null` —
  no circularity, pinned by a test that would read frame 75 instead of 130 if it voted). Marker
  drags re-derive on the next build (tested through the store/build path). No lifecycle ⇒
  marker-less behaviour + the Inspector explains why. `data-cg-poster-ms` is refined to the exact
  derived `H` for a follow video.
- **Inspector (both kinds, same presentation):** "Follow composition" in every state, the derived
  window read-only with comp equivalents, ONE "hold at" input seeded from the SHARED
  poster/midpoint helper (asserted as the shared CALL, not equal numbers), clamp hints through
  the existing machinery, "Detach — edit as manual", and the no-lifecycle explanation (§9.1).
  `contentStartDefault` was EXTRACTED (`content-start-default.ts`) so the follow hint and the
  Playout pin share the keyframes-only default.

## 2. ⚠ One deliberate divergence from the brief — say if you want it otherwise

The brief's parenthetical called the phase-source control "Lottie's **select**". There is no
phase-source select in the tree — the shipped control is state+buttons ("Add phase markers",
"Clear phase marks", a "from markers" row the E2E asserts by TEXT), and the follow transitions
are one-way gestures a select would misrepresent (markers is not re-enterable after a Detach
bakes over it; leaving follow is a bake, not a toggle). So "Follow composition" and "Detach" are
BUTTONS, same presentation in both kinds. Recorded in design.md §9.

Also: **Detach bakes `introEnd = outroStart = H`** (`holdAt` kept, so re-attaching restores the
hold time). The offset intro and bounded outro are follow-only capabilities the manual model
cannot express, so the hold — the load-bearing look — is what lands.

## 3. 🔴 Found beside the work, fixed with tests (the session-R adjacency)

`mediaHoldItem.infinite` — the line the follow case had to extend anyway — overstated infinity:
a MARKER-LESS `idle-loop` Lottie was listed infinite, but `clipPositionAt` loops only a NON-EMPTY
idle span; the zero-span fallback FREEZES and RESOLVES `whenComplete`, so the graphic
auto-closes while the alert claimed it never would (the same "renders something plausible" shape
session R catalogued). The predicate now spells the driver facts per kind — video `loop` is
infinite always (its loop branch never resolves, even zero-span) EXCEPT under follow with no
authored idle (the runtime freezes it at `H`); Lottie `idle-loop` needs a non-empty effective
span. Two shipped fixtures were corrected with the fix: session R's idle-loop Lottie now carries
a real idle span (the property its test names), and one `playout-content-drivers` fixture had an
ILLEGAL element — a Lottie with `holdBehavior: 'loop'`, the VIDEO spelling — that only matched
the coarse predicate by accident.
