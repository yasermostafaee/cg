## 2. 🔴 The finding — a marker-less Lottie goes blank at the end of its own playthrough, on EVERY surface

You reported that a Lottie's visible duration in the Preview equals `holdMs`, and asked me to record
the mechanism: content starts at the entrance-settle frame, which defaults to the out-point, so the
clip gets exactly `holdMs` of screen time.

**That mechanism is false.** Checked three ways before discarding it:

- `startOwnContent` starts `scopeTickers`, `scopeClocks`, `scopeSequences`. No Lotties.
- the content-start VISIBILITY gate collects hosts from `scope.tickers`, `scope.clocks`,
  `scope.sequences`. No Lotties.
- the play path starts every Lottie at PLAY, with a comment saying so: _"the Lottie intro starts at
  PLAY (not at hold entry like the time-driven content)"_.

**`lifecycle.contentStart` has no effect whatsoever on a Lottie.** I measured the real runtime under
a fake clock rather than argue it — scene 25 fps, out-point 60, `holdMs` **5000**, one clip whose
own length is 2000 ms:

| t (ms) | marker-less clip            | marked clip (`introEnd` 40) |
| ------ | --------------------------- | --------------------------- |
| 250    | frame 12                    | frame 12                    |
| 1000   | frame 50                    | frame 40 (settled)          |
| 2000   | **frame 100 = `op`, blank** | frame 40                    |
| 5000   | frame 100, still blank      | frame 40                    |

The clip paints from PLAY, and what bounds its visible life is **its own length**. `holdMs` was 5000
in both columns and bounded nothing. Where your clip's length sat near your `holdMs`, the two
coincide — which is how the report reads as it does.

### Both proposed levers were wrong, in different ways

- **Lever 1 (pin `contentStart` earlier) is a no-op for a Lottie.** So this observation does **not**
  motivate D-133 task §1, and I have written that correction INTO the D-133 item rather than the
  motivation you asked for — a false motivation in a PRD item outlives the session that put it
  there. §1 is still worth building; just not for this.
- **Lever 2 is reachable today**, so "neither is reachable" is false: `drivesHold` is authorable on
  the Lottie inspector (`StyleSection.tsx`), and setting it makes `hasContentElement` true, which
  reveals the Hold-source select. But it does not solve this either — a content-driven hold ends
  when the clip's intro completes, which for a marker-less clip is the moment it goes blank. It
  shortens the composition to the clip; it does not keep the clip visible.

### What the operator actually lacks

**Phase markers, and the inspector will not let them add any.** `StyleSection` renders editable
`introEnd` / `outroStart` inputs only when `phases.source === 'manual'`. A clip with no phases at
all gets a hint — _"No phase markers — plays once then freezes."_ — and no control at all. So an
imported clip with no markers plays once, goes blank, and nothing in the UI changes that.

Two directions in `design.md` §4.5, **no item number minted**:

1. **Offer MANUAL phases for a marker-less clip.** The editor already exists and is already the
   right shape; it is simply not offered when `phases === undefined`. Changes no runtime behaviour.
   **Recommended.**
2. **Change the marker-less `introEnd` fallback** so the freeze lands somewhere visible. Cheaper to
   implement, worse to decide: it silently changes what goes ON AIR for every existing marker-less
   clip.
