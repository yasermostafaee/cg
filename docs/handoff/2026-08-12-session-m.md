## What the answers cost, in corrections

Writing four answers into the spec meant re-reading the tree, and the tree disagreed with the
design in four places. All four are corrected at the source AND at every site that had built on
them.

**1. `hasContentElement` DOES count opted-in media.** §1.5 recorded "ticker / sequence / countdown
clock only — no Lottie, no video". False: it returns true for a `video`/`lottie` with
`drivesHold === true`, exactly as the canonical predicate does. Two things were built on the false
version and are now withdrawn — §3.5's "removing the gate is also a bug fix", and §8 risk 5 — plus
one spec scenario's surrounding claim.

**The real divergence, which does exist, runs in BOTH directions:** `hasEffectiveHoldDrivers`
honours `drivesHold !== false` for ticker / sequence / countdown clock and `hasContentElement` does
not read the flag for them at all (a `drivesHold: false` ticker OVER-counts); and the canonical
predicate honours D-112 `holdOverrides` on a nested instance while `hasContentElement` cannot see
them (a force-excluded element over-counts, a force-included one under-counts).

**And `hasContent` gates THREE affordances, not one** — the Hold-source select, the
`ContentHoldChecklist`, and "Pin content start". D-133 removes it from the third only, so the
divergence SURVIVES at the other two. That residual is recorded in §8 risk 5 and deliberately not
fixed here; **no item number was minted for it** — that is yours to file if you want it.

**2. The keyframe-interval premise was stale by 5×.** §5.2 note 3 and §9.3 both rested on
`video-driver.ts`'s "~5 s keyframe interval on this project's assets", and §9.3 called it "a
measurement, not a guess". It is a measurement of an era that ended in July: every import since
converter revision `2026-07-24.3` is encoded `-g 25 -keyint_min 25` — a fixed 1-second GOP — so a
seek decodes ≤25 frames, not ~125. `video-driver.ts`'s comment is annotated **at its own site**, so
the next reader cannot re-derive the old cost from it.

**3. `fastSeek()` does not exist on this engine.** "Prefer `fastSeek()` where available" was a
recommendation for an API that is not implemented in Chromium and appears nowhere in this repo
(only in `node_modules` typings). It is **deleted**, not hedged — a "where available" that can
never fire reads as a live recommendation to the next implementer.

**4. §9.1's and §9.2's own cost statements were overstated.** §9.1 weighed option (b) against
"every existing shape-only composition carrying a `contentStart`" — an EMPTY set, since the gate
this change removes is what withholds the button that would set one; the real exposure is every
composition that HAS a driver and never touched the hold select, because `holdSource` defaults to
`timed` even with drivers present. And there are THREE hold states, not two: under `manual` and
`static`, `holdSource` is ignored entirely, so (b) has no defined duration there at all. §9.2
claimed this codebase uniformly refuses compound verbs; `changeMode()` already seeds an out-point
implicitly, in the same file. The distinction that actually decides §9.2 is **announcement**, not
principle — choosing `auto-out` announces you want an exit segment; authoring a loop range does
not.

## What was built (`e44afbf0`)

`tick(frame)` positions every Lottie. Three things about it are worth your attention:

- **The mapping is REUSED, not copied.** The arithmetic came out of `LottieDriver.tick()` into one
  pure `clipPositionAt(elapsedMs, mode)`; both the driver's own clock and the playhead call it.
  `tick` owns only the ANCHOR — the playhead as elapsed time, from `activeRange.in` for IN/HOLD and
  from `lifecycle.outPoint` for OUT. The clip is never rescaled onto the composition's markers.
- **The singularity is TESTED as a mechanism**, not as matching pixels: a spy on that one function,
  asserting both paths route through it. A fork would produce identical frames today and diverge
  later, which is exactly the failure a pixel test would wave through.
- **A live driver OWNS the frame.** `positionAt` is a no-op while a driver is running its own
  lifecycle or holding a frame it drove to. The canvas never sends `play`, but the same host page
  serves the Preview, and its `reset` handler re-ticks WITHOUT a `!playing` guard — so the guard
  lives in the driver, where a future message cannot bypass it.

**Recon answer worth keeping** (design §4.1): a Lottie handle **cannot** go stale across
`scene-replace`. B-137's shape needs a node that outlives a rebuild and is reparented into it —
that is `preview.ts`'s `videoPool`, which is why `VideoDriver` needs `live()`. There is no Lottie
pool; `scene-replace` rebuilds the runtime and every driver with it. The rule, stated so it
generalises: **a `live()`-style re-resolution is owed exactly where a HOST pools and transplants
nodes.**
