# Handoff — 2026-08-13, session Z (the Preview's dead stop/out: the lifecycle machine, not the transport)

## 1. The first broken hop, named: HOP 4 — the runtime refuses

All four hops were instrumented on the REAL generated preview document (the same string
`platform/preview.ts` builds for the modal and the canvas), executed with the real
`createRuntime` / `installCasparGlobals` injected for its module import. One run, read
top to bottom:

```
[HOP3] typeof window.stop = function   window.stop === nativeStop? false
[HOP3] typeof window.out  = function   window.cg present? true
[HOP2] scrub painted 2 stage nodes                     ← the listener is alive
[SEQ]  after play                       → play.start
[SEQ]  after out (mid background outro) → play.start,stop.start
[SEQ]  after re-play during that exit   → play.start,stop.start,play.start
[HOP4] stop after the re-play → []      ← NOTHING. no event, no hide, no cut
[HOP4] out  after the re-play → []      ← NOTHING
```

Control arm, same harness: let the exit SETTLE first (`stop.start`,`stop.end`) and then
replay → `stop` → `["stop.start"]`. It works. The difference is a single operator move.

Hops 1 and 2 were also excluded by the owner's own repair: "switching playout mode"
posts `scene-replace` through the IDENTICAL `post()` closure and the IDENTICAL
`contentWindow` (`PreviewModal.tsx:245` / `:348-364`). If the handle were null or the
document deaf, the mode switch could not restore anything either — so the channel is
provably alive at the moment stop is being dropped.

## 2. The mechanism

`play()` SUPERSEDES an in-flight exit, and the runtime implements that everywhere: it
bumps `exitGen` so the exit's continuation bails, clears `pendingExitOutro`, empties the
one-shot outro ledger, calls `restoreContent()` and re-cascades `play()` into every
controller. The graphic really does come back on air.

The lifecycle table alone did not model the move — `exiting` could reach only `stopped`
or `removed` — so `machine.transition('playing')` returned **false**, and `play()`
**discarded the boolean**. The machine stayed in `exiting` while the stage played. And
the first line of both `stop()` and `out()` is

```ts
if (machine.state !== 'on-air' && machine.state !== 'playing') return;
```

so from that moment BOTH were silent no-ops for the life of that runtime — no event, no
error, no log. Only a rebuild cleared it, which is exactly what closing/reopening the
preview and switching playout mode do.

**The trigger is the most ordinary loop there is**: stop (or let the scene auto-out),
then press Play again before the background outro has finished. On the owner's
`follow.cgproj` that window is the whole OUT segment — frames 525→716 at 50 fps ≈ **3.8
seconds** after every close. That is the whole of "intermittent, no known trigger".

## 4. The fix, and the class

1. **`lifecycle.ts`** — `exiting → playing` is legal. The table now models the move the
   runtime performs.
2. **`runtime.ts` `play()` — the tripwire.** The boolean is no longer discarded: if
   `play()` ends with the machine anywhere but `on-air`, the machine and the stage have
   diverged and it emits `error / lifecycle.play-not-on-air`. Unfirable by construction
   today; it exists so the next state that cannot reach `playing` announces itself
   instead of killing both buttons.
3. **The silence in the preview document** (`platform/preview.ts`):
   - Control branches are matched on the ACTION and then checked for deliverability.
     `typeof window.stop === 'function'` was never a guard: **lib.dom always defines
     `window.stop`** (the page-load canceller), so it read "installed" on a document with
     nothing installed and cancelled nothing, silently. The truthful test is
     `window.cg === runtime`; an undeliverable control now posts `control.dropped` on the
     existing `cg-preview-error` channel, naming which of the three faults it is.
   - The handler's `catch` no longer swallows — it posts `message.handler`.
   - The runtime's own `error` events are forwarded (`runtime.error`).
   - **The BOOT build is wrapped.** `await applyScene(<inline scene>)` sits ABOVE the
     `addEventListener('message', …)`, so a throw there aborted the module and left a
     live-looking preview whose every message was ignored forever. (Demonstrated
     accidentally in this session: one malformed element and the instrumented document
     printed nothing at all.) It now reports `boot.applyScene` and carries on to the
     listener, so the next `scene-replace` can repair the document.
4. **The never-strand invariant, made true of both implementers.** §D6.4.1 asserts
   `playOutro()` ALWAYS resolves; `LottieDriver` had **no wall-clock backstop** (the
   video driver has had one since the sync-lifecycle fix, and its comment names the
   consequence). Added, from the same shared `OUTRO_BACKSTOP_MARGIN_MS`. And the exit's
   await is now bounded **at the ledger entry** — one bound covering both awaiting sites
   (the runtime's `stop()`/`out()` and every controller's `beforeOutro`), emitting
   `error / exit.outro-timeout` and letting the exit proceed rather than stranding.
   Found by recon, **not** the owner's defect — his failure is entirely §2.

## 6. What is NOT closed

- **No B- number was minted** (out of scope this session) and there is no OpenSpec change
  dir for this fix. If you want the `exiting → playing` contract in a spec rather than in
  `lifecycle.ts`'s docstring + the engine docs, that needs a number you mint.
- The `[cg-preview]` diagnostics are consumed by **`CanvasArea`'s** window listener
  (`console.error('[cg-preview]', label, payload)`), which receives the modal's messages
  too because it is not source-filtered. If a surface ever hosts the preview without the
  canvas mounted, the diagnostics would have nowhere to land.
